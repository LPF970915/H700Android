## 亮度最高档回落及修正

首次单调性检查实际失败，证据保留：32→32、64→64、128→128、192→192、224→224，255却读回200。此时框架 BRIGHT/manual、mActualBacklight=255，非调暗或省电策略。端点复查248/250/254均精确，255重复两次回落200；Light ioctl 返回成功。

只在 Source64 独立派生 Light 中加入兼容处理：标准 RGB 换算保持不变，写驱动时逻辑255映射254，其余0～254不变。最高档与254同亮度，避免滑到最右端反而变暗；真正0仍为关背光。**这是保留显示栈的端点兼容规则，未证明核内精确原因，也未恢复原始255档。** 旧 BSP/原 Light 模块、kernel/DTB 均未改。

新增主机测试覆盖全部256个逻辑档的单调性、0关闭、RGB/alpha、四个 unsigned-long ioctl 参数和错误传播。增量构建 `h700-low-pressure-20261104-130202` / `images-result-v15.json` / `prepare-v18.json` 成功，耗时1分35秒，峰值约5.0GiB、swap0；审计 `130408` / `round2-audit-v11.json` / `round2-test-v18.json` 通过120项检查、21项主机用例，耗时1分43秒、峰值约3.0GiB、swap0。始终保持单核、CPU0–1、nice19、-j1、RAM6GiB、swap上限512MiB、idle IO。

实机仅替换已备份的 vendor Light ELF，短暂重启该服务，未重启 Android：32/64/128/192/224/248/250/254精确，255→254，往返254/255仍稳定。原旧 ELF 和审计提取物、安装日志、回退代码及新哈希均留本地；本次回退未触发，不计为回退验收通过。vendor 恢复只读，运行守卫新增当前 Light SHA。**该 ELF 跨整机重启保留尚未重验**，避免在当前待拔插阶段重新挂载 TF2。

当前卡是此前修正 Test1 **再加 Source64 Light 端点兼容 ELF**。源码和分区产物同步了修正；旧整卡 gzip 仍未重封，不会随 Git 更新自动改变。镜像不上传。

## 电源与发行检查发现

- CPU/GPU/VE/DDR/电池5个温区可读；CPU配置60/70°C被动阈值、115°C临界阈值，CPU/GPU冷却设备存在。本轮未升温触发保护，不能据配置存在判定保护工作。
- Android ThermalService 显示 `HAL Ready: false`，无有效缓存温度，仍需补齐框架热管理链路。
- USB样本报告电池100%、4081mV、30°C；准确性、充电电流/容量、低电行为均未验收。
- Hall GPIO已有 IRQ 条目；实际 IRQ wake能力仍未证明，`rgsp_android_bringup`锁保留，深睡/耗电未验收。未申请GPIO、改DTB或写 suspend 状态。
- 当前 `eng` / `test-keys` / `ro.adb.secure=0` / `ro.secure=0` / `ro.debuggable=1` / root / SELinux Permissive，明确仍是工程配置。本次未改变认证、root或SELinux。
- 当前样本未见ADB TCP5555监听，5037只绑定IPv4 loopback；这不弥补USB免认证的发行缺口。
