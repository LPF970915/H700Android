## 恢复后异常轴的候选诱因

`android/h700-android10/device/roc/rgsp/input/kernel/h700_stick_axes.c:78–121` 只在装载时配置 ADC 并校准；`:124–143` 使用 system_freezable_wq 轮询。全文件没有 suspend/resume、PM notifier 或恢复后寄存器复核，断开时才在 `:174–185` 归零。

`input/axis_math.h:4–12` 在中心为 2048、raw 为 0 的假设下会得到正满幅 32767，因此恢复后的异常 ADC 读数具有触发原生方向导航的能力。没有现场证据证明实际读到 0；该模块只写 X/Y/Z/RUDDER，不写 HAT，也不能解释所有无摇杆机型。

PM 顺序另经反向核对：参考内核 `kernel/power/suspend.c:459` 先完成 `dpm_resume_end()`，`:480–484` 再 thaw 并通知 `PM_POST_SUSPEND`；`kernel/power/process.c:212` 释放 freezable 工作队列。不能宣称现有 poll 在设备恢复前抢跑。若以后只在 POST 才新增恢复保护，首次 thaw 后 poll 仍可能先执行，必须从 PREPARE 暂停并取消 work，再核验恢复后放行。

`pinctrl-sunxi.c:1280–1356` 已有 noirq bank 保存恢复，不能假定 PIO 必丢；stock `sunxi_gpadc.c:1476–1502` 也有 resume 初始化，但附加模块要求 GPADC DT 节点 disabled，不能认为 stock 驱动会替它恢复。普通熄屏不一定进入 suspend，PM 加固也不能代替完整屏幕／锁屏生命周期处理。上述是代码审计边界，尚未证明实际预编译基础控制器的所有恢复分支。

## 修复方向与不能混淆的边界

当前最符合现有证据的待验证链路是：熄屏恢复时输入轴或释放状态异常 → 解锁后原生方向键转换开始／重新开始 → AT4K 对每个 DOWN 执行切换，首尾环绕将单向重复呈现为左右来回。**已证实后两段有这样的能力，第一段实际触发源及录像是否经过整条链路尚未证实。**

下一轮候选应先补应用／框架的实际 fallback 路径，单独再升级 Navigation 服务不足以覆盖普通 HOME。可验证的保护包括：同一次持续方向会话有有限截止，重复 MOVE 不刷新截止，结束时平衡释放已发按键，截止后对应通道观察回中才解锁。它会限制合法长按，需明确记录行为变化；不能使用“几百毫秒未收到 MOVE 就当松开”，因为正常绝对轴长按也可能不重报。

设备／source／HAT／杆的所有权、独立取消及待释放键应作为单独的第二项候选验证。先在桌面／自有页面验证作用范围，避免无差别改变游戏依赖的 joystick fallback。恢复清理必须考虑当前框架已有 CANCEL／失焦处理，不能把重复添加同样的 cancel 当成完整修复，也不能只在亮屏清一次而让后续异常样本立即重启。

服务内受阻样本观察和待执行热键清理可独立补强，但不能冒充普通 HOME 根因。ADC 恢复修复保留为定向候选；若实施，只操作模块拥有的配置、四轴及两杆按键，保留原中心校准和基础控制器，恢复失败保持附加轴中立。禁止唤醒重校准、过滤所有合法端点，或把本录像归因于 GPU／面板。
