# 方案 A 单卡黑屏失败与证据纠正

日期：2026-09-11，Asia/Shanghai。

## 实机结果

用户确认本次安卓单卡在 TF1 主卡槽仍未启动，按电源键黑屏、无可见反应。
本轮没有取得该次开机 UART，不能由黑屏确定 BootROM、Boot0、U-Boot、
kernel 或 Android 的实际停点。不能把它直接归因于电压或 TF 卡不稳定。

## 主机核实

- `out/rgsp-single-card-20260911/write-single-card-raw.log`：
  09:36:15 开始，写完分区后在 GUID 比较处抛出异常。
- 同目录 `single-card-finalize.log`：
  10:17:48 至 10:30:47，报告分区几何/GUID、ROMS 格式化和 p1-p4
  完整回读通过。这是该时刻的分区结果，不是下午启动区修订的回执。
- 同目录 `tf1-boot-area-8m.bin`：
  文件修改时间 14:49:31，长度 8388608 字节。
- `tools/write_rgsp_single_card_raw.ps1`：
  修改时间 15:28:21；当前代码复制前 8MiB 后重写主 GPT，并写卡尾 GPT。
  当前代码存在不代表此前执行的脚本版本包含这些动作。
- `tools/finalize_rgsp_single_card_raw.ps1`：
  不复制 Boot0/启动包，不校验前 8MiB；它会格式化 p5，不是只读工具。
- 本轮 Get-Disk 只显示两块内部硬盘，失败 TF 卡未接入电脑；
  没有读取实卡或执行设备写入，也没有编译或发送串口命令。

因此此前“完整写卡成功，可以上机”的放行依据不足，相关当前状态已经纠正。
未发现新回执不等于已经证明实卡缺失 Boot0；必须用实卡读回区分。

## 校验方法缺陷

1. p1-p4 的哈希范围不包含 p1 之前的启动区。
2. 当前写卡脚本会替换源文件前 2048 字节的 MBR、GPT header 和 8 项
   GPT entries。因此不能拿新卡整个前 8MiB 哈希直接等同原 TF1 捕获哈希。
   后续应在普通文件中合成预期头部，再逐范围比对 GPT 与保留启动载荷。
3. 原 TF1 捕获的 GPT 含 `special`、`boot-resource`、`env`、`boot` 等
   8 个分区；新布局仅有 boot/system/vendor/data/ROMS。必须查明原固件
   对这些被移除分区和保留区的依赖，不能假设复制 8MiB 即满足所有条件。
4. 原卡 GPT 的首分区起点是 LBA 73728，新方案 boot 起点是 LBA 16384。
   起点差异本身不是已证实的错误，尚需启动包范围和实际读取路径证据。

## 下一步

1. 保留失败卡，不格式化，不清理日志，不重跑全卡 writer/finalize。
2. 重新连接读卡器后按序列号、容量、USB 类型重新识别目标，先只读备份
   前部区域、主/备 GPT 和可用的启动日志，并记录大小与哈希。
3. 对照原 TF1 捕获，检查实卡 Boot0 标识及完整载荷范围；按现用布局
   合成预期头部，分别比较 GPT 和不应变化的启动区域。
4. 有当前开机 UART 时定位第一个确定性失败；没有 UART 时不声称
   “完全没上电”或“肯定没写 Boot0”。COM4 存在不证明设备接线完好。
5. 找到差异后另行形成最小写入和回退方案，不重编整个 Android。
   写后须有本轮时间戳、脚本/输入哈希、目标身份、范围和完整回读回执。
6. 再实机验证。Linux 工作卡保持作为独立恢复介质，不能写入试验内容。

发布和 AT4K UI 精修继续以启动修复与基础回归为前置条件。

### 已发现的布局问题

本地源码
`work/h700-source-analysis/h616/longan/brandy/brandy-2.0/u-boot-2018/include/spare_head.h`
第 66、67 行定义启动包位置为 LBA 32800 与 24576：

- LBA 24576 = 12582912 字节，即 12MiB；
- LBA 32800 = 16793600 字节，即 16MiB + 16KiB。

这两个位置均在现卡 p1 `[8388608, 75497472)` 内。
从完整 p1 捕获检查，两处无 TOC1 magic；对应内容与已写入的 Android
boot 镜像相同。8MiB 源捕获根本没有覆盖这些候选位置。
原厂成功 UART 曾记录 `Loading boot-pkg Succeed(index=0)`，随后装载
u-boot、monitor、dtbo、dtb。不能用只含 Boot0 的捕获替代整条启动链。

这是确定的布局冲突与捕获缺口。实际原机启动包位置、有效长度、校验和
和此次上机首个失败点仍需原 Linux 卡及开机 UART 佐证，不把 donor
源码常量直接当成所有 RGSP 固件的实测地址。
