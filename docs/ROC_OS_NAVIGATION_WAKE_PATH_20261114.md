# 0.0.1 导航乱跳：熄屏、亮屏、解锁路径复核

2026-11-14，用户补充触发线索为“熄屏后亮屏、解锁可能乱跳”，并明确这是原 **0.0.1 发布版**反馈。当前 USB 连接的 34XXSP 已安装 Navigation17；本轮没有观察到该修复版出现原故障。用户随后完成三次实体操作并反馈“重复三次未见异常”。

结论：**旧版的方向连发状态可能跨屏幕状态残留，是与这条线索最吻合、且已有源码证据的缺口；当前 v17 已实施对应阻断。本机短时验证未见恢复后持续连发，但尚未捕获原发布版故障态，不能唯一归因于某条驱动或归零事件丢失。** 本轮保留 v17，不增加未经证实的输入过滤，也不更改内核、显示或电源策略。

## 旧版为什么符合这个症状

已与实际旧系统 APK DEX 核对过的方法，保留在 `out/nav-fix-20261114/prechange/build-support/public/overlay/device/roc/roc_os_source64/Navigation/src/com/roc/rgsp/navtrial/NavigationService.java`，SHA-256 为 `26010678339217441cae7f0a610c2c7a1f2704db6b0c7ca78da9d6b84cb05464`。

| 旧版位置 | 行为 | 对熄屏恢复的意义 |
| --- | --- | --- |
| `FocusRing.repeat`，1320–1325 行 | 保存一个 `axisKey`；每次自行生成 DOWN/UP 后，再排 160ms 回调 | 无需继续按键或新增 MOVE，也可以持续导航；循环自身不复核屏幕、锁屏、窗口或设备 |
| `applicationRoot()`，283–285 行 | 屏幕不交互或锁屏时返回空 | 当次导航无法找到托管页面；这个判断本身不清 `axisKey`，也不取消回调 |
| 服务生命周期 | 没有 `SCREEN_OFF`、`SCREEN_ON`、`USER_PRESENT` 接收器 | 不能直接在这三类状态切换时保证清理 |
| 中立、CANCEL、失焦、窗口状态、配置变化 | 原有停止路径确实存在 | 故障要求正常清理未生效，或清理后又被异常输入重新启动；不能写成“旧版从不清理” |

因此，一个符合源码的条件链是：方向状态进入重复器 → 归零/取消未清掉它 → 锁屏暂时挡住实际页面导航 → 任务继续保留 → 解锁重新出现托管页面 → 可见滚动恢复。此前直接执行原样提取方法的主机探针，单次 HAT_DOWN 后不再提供中立，在虚拟 60 秒内产生 374 对合成事件，证明了旧循环的持续能力；它没有模拟真实 Android 休眠、焦点分发或硬件，不能算本次触发路径实机复现。

同一个固定方向也不能单独解释真正的上下正负交替。若反馈里的“上下乱跳”确实是方向交替，还要区分异常轴值、原生重复与滚动后焦点重选。

## v17 的对应处理及剩余边界

实际候选文件为 `build-support/public/overlay/device/roc/roc_os_source64/Navigation/src/com/roc/rgsp/navtrial/NavigationService.java` 和 `AxisNavigation.java`，本轮只读复核：

- 三类屏幕广播均调用统一停止，清除排队任务及相关按键状态；失焦、窗口切换、设备变化也停止。
- 每次自有轴连发前检查当前交互、锁屏、托管页面、焦点、原窗口和设备；导航同步引发取消后，旧回调不能重新排队。
- 被停止的非中立通道须先归零；一次自有连续轴会话最多十秒，重复 MOVE 或反向不续期。
- 被动刷新不再执行 FOCUS/SHOW，相同选框不重复重绘。

两个边界需要保留：

1. 已知中立或此前未知的通道允许恢复后的第一次新按键；并非所有输入都必须额外发送一次中立。当前 MOVE 的一秒时效检查也没有精确的解锁代际边界。解锁前产生、短延迟后到达的非零样本理论上可能启动一次有上限的会话，尚未观察到。不能简单用广播接收时刻作界线：实际解锁到接收器执行之间存在异步投递，合法首按可能已经产生，严格过滤会误吞它。
2. 外部 DPAD KeyEvent 可能来自硬件或 Android 原生 joystick 合成，不属于 `AxisNavigation` 的十秒上限。若未来现场增长的是 `external-key`，必须对照 device/source/scan/repeat/flags 和原始输入后再修，不能宣称 v17 已约束系统中所有来源。

另一个排除项：保留的 Android10 InputDispatcher 先处理按键 UP 的重复状态复位，再判断屏幕策略是否允许投给应用。所以“屏幕策略不把 UP 交给应用”本身不足以解释它的全局重复一直保留；需要更具体的丢失或状态证据。

## 本机实际验证

所有记录保持同一 boot、同一导航 PID 及诊断版本38，没有重启、强制 suspend 或安装新版本。完整机器分析及原件 SHA 见 `out/nav-wake-path-20261114/acceptance.json`，可用同目录 `analyze.py` 从保留快照重新计算。

### 软件对照

执行普通 `input SLEEP` / `input WAKEUP` / `wm dismiss-keyguard`，与实体 A 解锁分开统计。

| 请求轮次 | 实际覆盖 | 结果 |
| --- | --- | --- |
| 第1轮 | 开始前已处于 Asleep/OFF，随后唤醒；keyguard 已解除，没有新增 USER_PRESENT | 只能算一次已有息屏状态的唤醒，不能算完整解锁循环；唤醒后约12.7秒无持续导航 |
| 第2轮 | 新 OFF → ON 且 keyguard showing=true → USER_PRESENT，showing=false → 静置 | 一次完整软件锁屏循环；解锁后约11秒无持续导航 |

十份阶段快照的 keyDown=227、callbacks=233、selectionActions=271、axisImmediate=53、axisRepeats=167 均不变；轴 inactive、repeatQueued=false。每份 `getevent -lp` 离散快照的九个绝对轴当前值均零。环形 trace 按时间去重，没有将旧事件重复计数。该时间区间的有限 logcat 中没有旧 crop/bind/Aborting GPU、FATAL EXCEPTION 或 ANR 签名。

准备时一次 `input ENTER` 未能解除定制锁屏，已保留结果；软件对照随后明确改用标准 `wm dismiss-keyguard`。注入 ENTER 不含实体 A 的 scan304，不能把它未解锁算成导航故障。

### 用户三次实体操作

用户回复“重复三次未见异常”。随后取得的导航轨迹保留三组新的亮屏和 USER_PRESENT，三次均有真实设备2的 A/ENTER DOWN、UP；原始 `lastInput` 也为 `66/304/UP`。

| 次序 | SCREEN_ON → USER_PRESENT，设备 uptime ms | 记录边界 |
| --- | --- | --- |
| 1 | 4967856 → 4970232 | 承接先前超时息屏；不是新记录的一次严格十秒熄屏 |
| 2 | 4981211 → 4983466 | 上一个 OFF 为4977515；日志记录 Hall CLOSE/OPEN |
| 3 | 5003080 → 5005297 | 上一个 OFF 为4996157；日志记录 Hall CLOSE/OPEN |

因此这是三次实体恢复/解锁的正常反馈，不能写成三次精确十秒、纯电源键或深睡验收。最后一次解锁到收尾快照约20.8秒。

`axisRepeats` 始终为167，没有新增自有连发。期间还记录到两次短 HAT_DOWN，每次均完整归零；`axisImmediate` 53→55，与这两次输入吻合。另有一次解锁后 A 操作，页面发生切换；所以总按键、动作、重绘计数有所增加，不能笼统写“所有计数不变”。收尾轴均零、axisActive=false、repeatQueued=false、屏幕 ON、锁屏已解除，服务及 boot 未变。

### 原始输入覆盖限制

90秒有界采集 `out/nav-fix-20261114/captures/20261114-021950-768/` 成功完成67份状态样本，reader 精确清理确认。原始事件0行仍记为覆盖未知，不能声称内核零输入。

该 reader 在上述软件轮次和用户三次实体操作前已结束。准备阶段的 WAKEUP/ENTER 注入发生在90秒窗口内；采集脚本自身不注入，不等于整个窗口没有其他普通框架操作。本轮只能用分阶段的内核轴快照、导航内存轨迹、有限 logcat 和用户反馈关联后续操作，不能将这段 raw 冒充为后续全程输入流。

## 故障闭环的范围

已确认并修复旧服务的持续重复能力及生命周期缺口；新增触发线索与这条机制相符，当前 v17 的软件对照和三次实体恢复均未见异常。原发布版究竟在哪一步漏掉中立/取消，或是否由恢复后异常轴值、外部原生重复触发，仍无故障态证据。USB连接及保留 trace 的时钟差不能证明经历了真实深睡；跨机型和长期偶发验收也仍未完成。

附加摇杆模块没有专门恢复校验，是待观测的次级候选，但只写摇杆轴、不写 HAT，且不能解释所有无摇杆机型。本轮未据此修改驱动。整屏频闪仍未复现、未定性；没有将导航恢复正常推断为 GPU/面板已修复。

后续若再出现，保留故障态并按 `axis-repeat`、`external-key`、内核非零轴或无输入的刷新循环区分。当前无需以重启证明修复，也没有重新制作整卡镜像。
