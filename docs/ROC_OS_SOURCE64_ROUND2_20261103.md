## 存储与启动契约

TF1 保留必要的前六个分区和原有起点，p7 改为 `userdata` 并使用剩余空间；紧凑 GPT 仍占八个槽位，最后一个槽位为空，不再建立 p8 ROMS。TF2 通过 `sdc2` 控制器识别，不能依赖 Linux 的 MMC 序号或固定 minor。

当前契约沿用 32,434,554,368 字节的种子几何，实际使用应准备至少 64GB 的 TF 卡；不能据镜像逻辑长度宣称兼容所有标称 32GB 卡。若以后要求更小卡容量，需要另做缩小种子与容量边界验收。

扩容工具先验证新布局身份、原分区边界和文件系统 UUID。GPT 采用备份先写、同步并回读、再提交主表的流程；分区表重读失败时要求重启后再扩展文件系统。文件系统增长在挂载前执行检查和 resize，不自动格式化、不迁移现有工作卡。错误身份、旧 p8、边界变化或双表损坏必须拒绝。

松散启动契约保留原硬件启动前段，仅替换 TF1 识别、容量准备和 by-name 链接。需要将三份已检查的 ARM64 静态工具放入未来 ramdisk，并赋予可执行权限。源码构建产生的 `ramdisk.img` 仍不能直接替代这份定制启动契约。

## 编译与复审方法

所有编译和完整分区复审均使用低负载入口：合计单核、CPU0–1、`-j1`、nice19、RAM6GiB、swap512MiB、idle IO。没有提高电压、频率或资源上限。

```powershell
.\tools\build_h700_low_pressure.ps1 -Targets H700Source64Build -Execute
.\tools\build_h700_low_pressure.ps1 -Targets H700Source64Audit -Execute
```

20 项主机检查覆盖三种卡容量、GPT 幂等与主表损坏恢复、拒绝错误布局、真实 ext4 增长后哨兵文件保留、TF2 控制器分类、背光 ABI，以及初始化中断重试、锁释放、自定义选项保留和错误机型/镜像拒绝。

分区复审直接读取生成镜像，检查 fsck、实际 APK/DEX、服务类路径、HAL 声明、init 服务唯一性、文件标签、旧入口与预优化残留、全量安装 APK 目录、保留的双 ABI 运行库、静态启动工具，以及链接命名空间和新守护进程的强未定义符号名称。它不证明全部符号版本、动态 dlopen 路径、内核 ioctl、上机行为或正式发布安全性。

ARM64 工具模拟执行只访问新建的普通元数据/文件系统夹具，未访问块设备。它验证了实际 Android 二进制的用户态行为；未来工厂 userdata 的文件系统特性、H700 内核兼容性、真实断电和首启扩容仍须在封装及备用卡阶段验证。属性审计按本 BSP 的 `default.prop` 回退、后加载覆盖和分区型号派生顺序执行，而非套用 GSI 的文件布局。

第一轮三份镜像及原产品归档、371 个原始输入和两份真实 ABI5 主机库继续受保护。失败编译、失败审计、每次派生源码、被移出候选的旧文件和原始记录均保留；`SPACE_REVIEW` 用户修改不纳入本轮提交。

## 复审过程中拦截的问题

- 私有 Light/vold 复用旧安装文件名造成规则冲突，改为独立名称。
- 私有 vold 将 `std::string` 与空指针比较，修为控制器路径判断。
- 继承标记重新带入旧 SystemServer 类路径，改为显式四条列表。
- Wi-Fi 强制安装旧服务 jar，增加只改模块依赖的私有 Wi-Fi 模块。
- 旧 Make 不扫描已有 Android.mk 下的子目录，导致类路径指向不存在的私有 Wi-Fi jar；补上独立产品的显式 include，并增加每条类路径文件/服务类存在性检查。
- 核心服务的 priorityboosted 规则仍通过冒号模块引用旧 unboosted core，最终 DEX 未含存储修正；同步该引用，要求最终 DEX 与 vold 二进制都含新的控制器策略。
- 继承链中的 vendor 路径占位符在后期才解析，旧 fstab/mixer 抢先生成复制规则；将独立产品替换项前置，按最终分区中的内容和哈希验收。
- 复制优先级修正显露出 32 位 Mali 源路径指向另一个变体；显式选择与已验收系统及第一轮实际产物同 SHA 的 `arm/lib`，64 位仍保留原 SHA。

上述失败不归类为设备启动失败，也不因 Ninja 成功就跳过分区检查。
